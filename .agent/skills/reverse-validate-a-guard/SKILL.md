# 证明守卫真的会红

## 什么时候用

任何「检查存在」的时刻：新增架构规则、清单校验、正则 gate、CI 断言、lint 规则。
**判据不是"测试通过了"，而是"把违规注入进去，测试会红，而且红的正好是那一条"。**

三类症状都指向这里：

- 测试全绿，线上还是坏了 → 守卫从来没触发过
- 把缺陷注入进去，测试没反应 → 守卫看不到它守的东西
- 没改代码，测试却变红（或明明改了却不红）→ 断言描述的不是你以为的那个对象

## 五步流程

```
1. 记下基线：跑一遍，确认 0 failures（别记断言数，会随套件增减变化）
2. 注入：制造**一处**违规，最小改动
3. ★ 断言注入成功：确认目标确实从 N 变成 M，否则中止（见「假绿 5」）
4. 跑测试：红的必须是**预期的那几条**，数量与名字都要对
   - 全绿 → 守卫是摆设
   - 红了一大片 → 注入改动面太大，重做成单点
5. 恢复：还原，**断言恢复成功**，再跑一遍确认回到基线
```

第 3 步和第 5 步最容易被跳过，而它们恰恰是最常出问题的地方。

## 七种假绿（全部实测踩过）

### 1. 文本匹配绕过了结构

守卫用字符串匹配，而被守卫的代码有**同一意图的另一种写法**。

```js
// ❌ 只匹配一种拼法
spec.includes('= "default"')        // 漏掉 siteId = DEFAULT_SITE_ID
spec.includes("/extensions/plugin/") // 真实写法是 "../plugin/runtime"，不含 /extensions/
```

**修法**：解析结构而不是匹配文本——按文件路径解析后比较目录，用 AST，用类型系统。

### 2. 对空集合的检查是空转

守卫逻辑完全正确，但它遍历的集合是**空的**——检查了零次，永远绿。

```js
for (const owner of readdirSync(baseDir)) {   // baseDir 是空目录
  // 里面写得再对也没用
}
```

**修法**：先断言集合非空（`check("至少有一个样本", items.length > 0, true)`）。
加一条"至少检查了 N 个对象"的元断言，比守卫本身更重要。

### 3. fixture 有多处差异

反向验证时删掉被验的那一半，测试**依然全绿**——因为两个 fixture 在别的维度上也不同，
被删的那一项在这一次比较里是多余的。

> 实例：为「归属隔离」写的用例，拿**主题 owner** 对**插件 owner**。于是把 `WHERE` 里的
> `owner_name` 整条删掉，测试仍绿——两个 fixture 的 `owner_type` 本来就不同。

**修法**：被删掉的那一项必须是**唯一区分两个 fixture 的那一项**。
写用例时先问：「我把这一条删了，哪个断言会变红？」答不上来就是 fixture 没设对。
（修正方式是再加一个**同类型**的第二个对象。）

### 4. 断言描述的是上一轮的产物

**最隐蔽的一种**，不在被测代码里，也不在 fixture 里，而在"测试到底在看哪个文件"上。

> 实例：套件开头 `rmSync(dir, { recursive: true, force: true })`。Windows 上这一步会因
> `EBUSY` 失败，而 `force: true` **把错误吞掉**。被测的生成器又刻意拒绝覆盖已存在的文件，
> 于是残留的旧文件全部存活——**整套断言描述的是这一次根本没有写出来的内容**。

症状极具误导性：套件全绿；而把缺陷注入生成器之后，红的是"另一件事"。

**修法**：**清理之后要验证清理成功**。

```js
rmSync(dir, { recursive: true, force: true });
if (existsSync(dir)) throw new Error(`could not clear ${dir} — assertions would describe a stale tree`);
```

凡是"先清空再生成"的套件，都必须能区分"这次生成的"与"上次剩下的"。
同理适用于：构建产物目录、快照目录、临时数据库、被 `force` 掩盖的任何删除。

### 5. 注入脚本自己没注入成功

> 实例：注入脚本打印 `closers removed: 2 -> 2`——它什么都没改，
> 而我把随后出现的红色当成了证据。那次"反向验证"证明的不是我想证明的东西。

**修法**：注入后断言目标数量确实变了，恢复后同样断言。

```js
const before = (src.match(/pattern/g) ?? []).length;
if (before !== EXPECTED) throw new Error(`expected ${EXPECTED} targets, found ${before}`);
const after = src.replace(...);
if ((after.match(/pattern/g) ?? []).length !== 0) throw new Error("injection failed");
```

**不能证明自己注入成功的注入，不是注入。**
把注入/恢复写成一个可重复执行的脚本（`inject.mjs inject|restore`），而不是一次性命令——
一次性命令里一个转义错误就会静默变成 no-op。

### 6. 没有摘要行的一跑，被当成了通过

**读测试结果的那一层也会骗人**——不在被测代码、fixture 或"看哪个文件"上，
而在"我怎么判断测试过了没有"。

> 实例：套件的摘要在 `main()` 末尾打印。模板渲染一旦抛错（未闭合的 `{{/section}}`
> 会让引擎直接抛），控制流跳出，**`N passed, M failed` 这一行永远不会打印**。
> 校验脚本用 `grep '^[0-9]+ passed'` 读结果——匹配不到就什么也不输出，
> 而"没有输出"被读成了"没有失败"。**同一次会话里犯了两次。**

**修法两层，缺一不可**：

1. **套件侧**：摘要抽成函数，`catch` 分支里也调用它，并把异常计为一条失败（标 `(aborted)`）。
   **任何一跑都必然有摘要行**。摘要格式必须跨套件统一——有的套件只打 `N failure(s)`
   没有 passed 计数，脚本就分不清"绿"和"崩"。
2. **校验脚本侧**：把「**摘要行缺失**」当作 FAILED，而不是跳过。
   **没有摘要 = 失败**。`grep` 匹配不到，是"我不知道"，不是"它没事"。

### 7. 守的是「写法」，不是「语义」（第 1 种的复发形态，最容易被自己骗过）

第 1 种说"文本匹配绕过结构"，于是你把守卫写得更严——但**只严在一种写法上**。
真实案例：零容忍检查 `siteId = "default"` 参数默认值，**匹配不到 `o.siteId ?? "default"`**。
问题**没被消灭，只是从 `=` 被挤进了 `??`**。扩展守卫后一次抓到 9 处，
其中 2 处是人工审查漏掉的。

同族还有两个**写守卫时自己会踩**的坑：

```js
// ❌ 尾 \b 在引号后恒不成立：(?:default|en)"\b —— \b 要求两侧一为词字符
/\b(siteId|locale)\b[^\n]{0,120}?(\?\?|\|\|)\s*(?:"(?:default|en)")\b/
// ✅ 去掉尾 \b，或改为匹配运算符本身
/(?:^|[^\w$])(?:siteId|locale)\b[^\n]{0,120}?(\?\?|\|\|)\s*(?:"(?:default|en)")/
```

```js
// ❌ 豁免范围守卫只统计「带标记**且有违规**」的文件
//    → 第二个文件**没有违规就能白拿豁免**（靠违规的缺席来生效）
for (const f of files) { const hasMarker = /*...*/; for (const m of matches) { if (hasMarker) exemptions++; } }
// ✅ 统计**标记本身**
for (const f of files) { if (raw.includes(MARKER)) exemptFiles.push(f); }
```

**修法（三条，都很便宜）**：
1. 守卫要覆盖**同一意图的每一种写法**：`=`、`??`、`||`、三元、常量形式。
2. 新增一条守卫后，**逐写法实测样例**（`node -e` 跑一批字符串），
   **不要靠推断**——推断会得出"已覆盖"的错误结论。
3. **守卫自身的守门逻辑也要反向验证**。尤其小心：
   **一个只在"没违规时"才通过的检查，看不见自己的范围失控**——
   它的通过条件依赖被检查对象是干净的。

**合法豁免写在源码里，不写在测试的例外清单里**：用 `// ARCH-RULE-EXEMPT: <理由>` 标在
那一行上方，再配一个**计数守卫**（全库只许 N 处）。理由是可见性——
例外清单写在测试里，读源码的人看不到它为何合法；两处都改才能扩大范围。

## 注入工具自身的三个陷阱（写 inject/restore 脚本时）

反向验证工具自己也会说谎。三个都实测踩过：

| 陷阱 | 症状 | 修法 |
|---|---|---|
| **字节数守卫看不见等长替换** | `"/shop/"` → `"/blog/"` 长度完全相同，守卫打印"什么都没改"，而注入**其实生效了**——防假阴的工具自己产出假阴 | 比**内容哈希**（`createHash("sha256")`），不比长度 |
| **`git checkout -- <path>` 修不了 untracked 文件** | 新文件 git 从没见过 → 还原**静默失败** → 每个场景叠加在上一个之上，观察到的失败清单是多次注入的叠加物，全部作废 | 用**快照/回拷**（`cpSync`），不用 git |
| **快照取自脏树** | 快照前忘了还原上一次注入 → 脏状态被**拍进快照** → 之后每次"还原"都忠实还原损坏 → 套件连红 N 轮在一个**没有任何场景引入过**的缺陷上 | 快照前跑 `assertPristine()`（对照套件断言的那几个性质），还原后**再**跑一次。**还原也要被验证** |

参考实现：`tests/_eshop-inject.mjs`（CFPress 仓库）——7 个场景，每个：
注入（哈希证明生效）→ 跑套件（红在预期断言）→ 还原（pristine 双向验证）。

## 用真实产物验证生成器

生成器（脚手架、代码生成、模板渲染）有一类特殊陷阱：**只以命令形式运行的生成器，
等于输出永远没被检查过的生成器**。

- 让生成器**可被 import**：`main(argv, io)` + 纯内容构造函数 + `isMain()` 守卫，
  用户可见错误抛类型化异常并转成退出码。这样测试能直接调它。
- 测试要用**真实的**消费者去跑生成物：真实校验器、真实渲染引擎、真实规则函数。
  **不要复制规则**——抄本永远先过期，"过了 X 检查"会从事实变成声明。
  两条路径需要同一个答案时，**共享定义，而不是共享结论**（把规则抽成函数，两边 import）。
- 断言顺序要覆盖：有数据 / 无数据各渲染一次；每个引用目标真的存在；
  输出里**不该残留模板语法**（`!out.includes("{{")`）。

## 做完之后

把新发现的假绿类型**写进仓库的 AGENTS.md / 测试文档**，连同修法。
这类知识只在被写下来之后才会累积——否则同一个坑会以略不同的形式再踩一次。
