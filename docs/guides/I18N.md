# 多语言（I18N）

本文展开 [`ARCHITECTURE.md`](../ARCHITECTURE.md) §2.4–§2.7 与 §5.4①，面向**改这块代码的人**。
设计与理由在那边；这里讲清**四层分别是什么、谁写谁读、以及每一条不变量为什么不能破**。

> 一句话总览：CFPress 有**两件互不相干的语言**——
> **内容语言**（前台的页面、文章）和 **界面语言**（后台的按钮、菜单）。混用它们是这块最常见的错误。

---

## 1. 四层模型（L0 → L3）

```
L0  站点语言开关        site_locales           哪个站点提供哪些语言、哪个是默认
L1  内容语言            posts / post_translations + {table}_i18n
L2  界面词典（四层叠加）  core ① → plugin ② → theme ③ → DB overrides ④
L3  后台界面语言        user/请求偏好 → ?ui= → cookie → 站点默认
```

| 层 | 存哪 | 谁写 | 谁读 |
|---|---|---|---|
| **L0** | `site_locales` | 后台 Languages 屏 | `resolveLocale`、`locales()`、编辑器语言条 |
| **L1** | `posts` + `post_translations`；主题自有表 `{table}` + `{table}_i18n` | 编辑器、`tableSave` | `findContent`、`runThemeQuery`、`tableList` |
| **L2** | ① TS 常量 ② `plugin.json` 的 `langs{}` ③ R2 `langs/*.json` ④ `i18n_overrides` | 平台 / 插件作者 / 主题作者 / 后台 | `createTranslator` → `t(key)` |
| **L3** | `?ui=` / cookie / 用户设置 | 后台语言切换 | 后台 SPA |

**L1 与 L2 的分界**：L1 是**内容**（这篇文章的标题），L2 是**界面文案**（"保存"按钮）。
一篇中文文章的英文字段属于 L1；把"保存"显示成 "Save" 属于 L2。

## 2. 语言是怎么选出来的（`resolveLocale`）

优先级从高到低：

| # | 来源 | 例子 | 未命中时 |
|---|---|---|---|
| 1 | **URL 路径前缀** | `/en/about` | **404**（见下） |
| 2 | `?lang=` | 无头 API、预览 | 落到下一个来源 |
| 3 | cookie | 记住上次选择 | 落到下一个来源 |
| 4 | 站点默认 | `site_locales.is_default` | —— |

### 为什么只有「路径」会 404

这是 `LocaleMatch.explicit` 存在的**唯一**理由：`explicit` 只表示"来自路径"。

- 路径是**访客明确说出口的**选择。给了 `/en/...` 却返回中文是**撒谎**，所以 404。
- `?lang=` 和 cookie 是**提示**。前者可能是别人发的链接里带的，后者可能是三个月前的。
  把它们当 explicit，一个过期 cookie 就能让**存在的页面**变成 404——自己给自己制造故障。
  所以未命中就继续往下落：**语言错了也比没有页面强**。

⚠️ **反过来的坑**：`isKnownLocale` 同时检查「形状合法」和「本站确实提供」。
只检查形状会让 `/xx/about` 被当成"xx 语言的 about"，把本该 404 的路径变成 fallback。

### 无前缀访问

`/about`（无前缀）按**站点默认语言**解析。这就是 `lang_group` 必须存在的原因：
`/about` 与 `/zh/about` 是**同一份内容**的两个语言版本，共用 slug，靠 `lang_group` 分组。

## 3. 内容语言（L1）：两条路径，一套规则

### 3.1 帖子 / 页面

```
posts                    ← 语言无关：id, site_id, type, slug, lang_group, status, 时间
post_translations        ← 语言相关：post_id, locale, title, excerpt, content
```

**slug 跨语言唯一**（§9 决策 1）：唯一索引 `UNIQUE(site_id, type, slug)`，**不含 locale**。

### 3.2 主题自有表

```
theme_{owner}_{table}          ← 主表（含可翻译字段的一份「默认语言镜像」）
theme_{owner}_{table}_i18n     ← 翻译表：row_id, locale, 可翻译字段
theme_table_defs               ← 逻辑名 → 物理表名，以及有没有 _i18n
```

### 3.3 三条铁律

| # | 规则 | 破了会怎样 |
|---|---|---|
| 1 | `{table}_i18n` **永不 drop、永不清回 NULL** | 切主题/停用语言就丢翻译，**不可恢复** |
| 2 | 主表只 `ADD COLUMN`，**从不删列** | 删列即丢默认语言的内容 |
| 3 | `theme_table_defs` **切主题不清** | 表还在、数据还在，但没人知道它存在 → 数据变孤儿 |

**可翻译字段同时存在于主表和 `_i18n`**：主表那份是**默认语言**的镜像。
这样**加一个语言不需要数据迁移**——`_i18n` 里没有行时读主表即可。

### 3.4 读取的兜底阶梯（只写一次）

```
请求语言 → 站点默认语言 → 主表里的值
```

实现在 `table-facade.ts` 的 `readProjection()`：两次 `LEFT JOIN` + `COALESCE`，
**不是**在调用点再查一次。翻译缺失是**常态**，代价是"没翻译的商品名让商品页 500"。

```sql
COALESCE(tr.name, dflt.name, m.name) AS name
LEFT JOIN theme_x_product_i18n tr   ON tr.row_id   = m.id AND tr.locale   = ?  -- 请求语言
LEFT JOIN theme_x_product_i18n dflt ON dflt.row_id = m.id AND dflt.locale = ?  -- 站点默认
```

### 3.5 写入是不对称的（别「优化」掉）

| 站点语言数 | 可翻译字段写到哪 |
|---|---|
| 1 种（无 `_i18n` 表） | **主表**——单语言站点的商品名本来就住这里 |
| 多种 | `_i18n`(请求语言)，**且只有当请求语言 == 站点默认时才同时更新主表** |

主表是**默认语言的镜像**。让一次英文编辑覆盖主表，就会**静默改写中文商品名**。

### 3.6 `lang_group`：这条规则必须只写一次

「没有 `lang_group` 就是它自己」这个判断，**JS 与 SQL 各有一份实现，且必须一致**：

- JS：`groupOf()`
- SQL：`GROUP_SQL`（`src/api.ts`）

⚠️ 只写 `WHERE p.lang_group = ?` 会**排除掉组名所指的那一行自己**（它的 `lang_group` 是 `NULL`）。
于是组看起来是空的，编辑器报告"缺少翻译"，**诱导用户再建一个已经存在的语言的副本**——
不报错，只是悄悄多出一份内容。

## 4. 界面词典（L2）：四层叠加

```
① core pack       platform/i18n/core-pack.ts（TS 常量，不依赖 R2）
② plugin packs    plugin.json 的内联 langs{}
③ theme pack      R2 themes/<name>/<version>/files/langs/<locale>.json
④ DB overrides    i18n_overrides（后台可编辑）
```

**后来者覆盖前者**。缺 key 时回退到 **key 本身**，不是空字符串——
屏幕上出现 `theme.shop.cart.title` 是**可排查的**，出现空白不是。

### 为什么 ② 是内联的而 ③ 是文件

`uploadExtension` 把**主题**的每个文件解包进 R2（`…/files/`），所以主题包就是**一次 R2 读**，
改翻译 = 重新上传，**不需要重新部署**。

**插件包按 zip 原样存、从不解包**——插件**没有目录可读**，只能把语言包内联在 `plugin.json` 里。

### key 前缀是强制的

| 来源 | 前缀 |
|---|---|
| 核心 | `core.` |
| 主题 `foo` | `theme.foo.` |
| 插件 `bar` | `plugin.bar.` |

**这不是风格要求**。两个扩展都定义 `nav.home` 时，谁生效取决于**加载顺序**，
而且**没有正确的修复位置**（两边都"对"）。架构测试直接读文件检查前缀。

### ② ③ 为什么通过「注入」到达

读主题包需要知道**哪个主题是活动的**，那是 `extensions/` 的知识；
而 `platform/` **不得 import `extensions/`**（§7.3 规则 1）。

于是 `platform/i18n/packs.ts` 只声明 `PackProvider` 形状，由 `index.ts`（唯一能看见所有层的模块）
在 boot 时注入：

```ts
setPackProviders({ theme: themePackProvider, plugin: pluginPackProvider });
```

**机制与 `contract/hooks.ts` 的 `setHostHooks()` 完全相同**：中间一个接口、boot 时接一次、
默认是 no-op。没有 provider 时词典就是 ①+④，正好等于"没有主题/插件在翻译任何东西"——
**调用点不需要 null 判断**。

## 5. 后台界面语言（L3）

后台 UI 语言与内容语言**互相独立**：站点内容可以是中文，而管理员用英文后台。

改动语言开关（启用/停用/加语言/改默认）之后**必须刷新后台上下文**（`loadContext()`），
否则 `state.locales` 这个缓存还是旧的，`loadVersions()` 会以为站点是单语言的，
**整个语言版本条不渲染**——屏幕上没有任何东西是红的，因为「少一块」不会报错。

## 6. 改这块之前，先跑这几个套件

```bash
node tests/suites/i18n.test.mjs            # 四层契约 + 翻译组 + 主题自有表
node tests/suites/multisite.test.mjs       # 站点隔离（语言与站点是正交的两个维度）
node tests/suites/manifest-validation.test.mjs   # 内联语言包 lang{} 的校验
```

### 已经踩过的坑（都留了守卫）

| 症状 | 成因 | 守卫 |
|---|---|---|
| 组看起来是空的 → 诱导重建翻译 | `WHERE lang_group = ?` 排除了自己 | `tests/suites/i18n.test.mjs` 第 9b 段 |
| 整个语言版本条不渲染 | 改了语言开关没刷新 `state.locales` | 浏览器验收脚本 |
| 单跑绿、按 `npm test` 顺序跑红 | 共享 D1 上的**全局计数**断言（`theme_table_defs` 不随主题停用消失） | 断言按 owner 收窄 |
| 翻译丢了，且不可恢复 | 误 drop `_i18n` 表 / 把列清回 NULL | 代码里没有这条路径；有就是 bug |

> **共享 D1 的注意点**：多套件跑在**同一个**本地 D1 上。`theme_table_defs`
> **按设计不随主题停用消失**，所以夹具必须删掉自己的注册行 **并且** drop 自己生成的表。
> 否则下一套件会看到上一套件留下的东西。

## 7. 快速自检

```bash
# 1. 语言开关
curl "$BASE/api/v1/i18n/locales?site=default" -b cookies.txt

# 2. 前台按语言渲染（注意 X-CFPress-Template 头）
curl -sI "$BASE/en" | grep -i x-cfpress
curl -sI "$BASE/zh-CN" | grep -i x-cfpress

# 3. 显式语言未命中 → 必须是 404，不能回退
curl -sI "$BASE/xx/about" | head -1

# 4. 主题自有表的翻译阶梯（第 3 个参数是 locale）
curl "$BASE/api/v1/theme-tables/product?locale=zh-CN" -b cookies.txt
```

第 3 条最值得盯：**回退是设计，404 也是设计**，两者搞混会得到一个"看起来能用"的假象。
