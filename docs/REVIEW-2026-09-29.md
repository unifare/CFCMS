下面 4 个高危项全部经过实读验证，并给出「何时会爆」的具体场景。

## H1（最严重）· `tableDelete` 静默销毁其他语言

```ts
// src/extensions/theme/table-facade.ts:338
export async function tableDelete(env: Env, def: ThemeTableDef, id: string): Promise<void> {
  if (def.i18n_table) {
    await env.DB.prepare(`DELETE FROM ${def.i18n_table} WHERE row_id = ?`).bind(id).run().catch(() => {});
  }
  await env.DB.prepare(`DELETE FROM ${def.table_name} WHERE id = ? AND site_id = ?`).bind(id, def.site_id).run();
}
```

三点问题，任一都足够：

1. **签名里没有 `locale`**。作为「数据访问函数」，它违反规则 6 的精神（虽然规则 6 的表层
   检查只盯 `siteId`/`locale` 的默认值）。调用方 `api.ts:945` 传的是 `(env, def, row.id)`——
   **删一行 = 删所有语言**。多语言站上，管理员删掉「日语版」这一行，中文/英文版本一起消失。
2. **`WHERE row_id = ?` 没有 `site_id` 收窄**。主表那条有 `AND site_id = ?`，
   侧表这条没有。如果 `row_id` 恰好跨站碰撞（生成表 id 若非全局唯一），会删到别的站。
   **一个函数里两条 DELETE 的收窄条件不一致，是明确的缺陷，不是风格问题。**
3. **`.catch(() => {})` 吞掉错误**。`_i18n` 删除失败时静默继续，然后主表删成功——
   留下**孤儿翻译行**。设计不变量说 `_i18n` 永不清理，于是这些孤儿永远活着，
   下次同 id 复用时**复活成脏数据**。

> ⚠️ 注意：不要用「`_i18n` 永不删除」去论证这里该保留。不变量的原意是
> **「不因切语言/切主题而销毁数据」**，不是「删行时也必须留副本」。
> 但**删单语言**与**删整行**是两件事，当前代码无法区分——因为签名里没有语言。

**建议**：`tableDelete(env, def, id)` 保持「删整行含全部翻译」的语义**但补 `AND site_id = ?`**，
另加 `tableDeleteTranslation(env, def, id, locale)` 供「只删某语言」；
两者都在 JSDoc 写明语义差异。**关键是让签名承载语义**，而不是让调用方猜。

## H2 · 主题 Worker 信任可伪造的头取 `siteId`

```ts
// src/extensions/theme/runtime-worker.ts:297
const siteId = request.headers.get("x-cfpress-site") ?? "default";
```

对照**正向路径**：前台走 `resolveSite(env, u, sites)`（`index.ts:112`，按 host/路径前缀），
后台走 `requestSiteId(url)`（`api.ts:60`，`?site=`）。
**`handleThemeApi` 是唯一一个数据访问入口，站点来源既不是 host 也不是 `?site=`，而是请求头。**

问题：
- 请求头是**客户端可控**的。真正能约束它的是「谁能调到 `/__cfpress/theme-api/*`」——
  如果这条路由没有绑定到沙箱调用方（如 service binding / 签名），任何能发 HTTP 到宿主的
  客户端都能**指定站点**，即跨站读写。
- 缺头时兜底 `"default"`，意味着**沙箱主题一旦漏传头，就静默操作默认站**——
  正是 AGENTS.md 里 `activeTheme()` 那个缺陷的完全同型：能编译、能运行、**静默读错站点**。

**建议**：`siteId` 必须由**宿主在调用沙箱时注入并验签**，或改为从 URL/路径解析，
**不接受裸头**；缺站点时**拒绝**（4xx）而不是兜底 default。
这条要落成检查：**「所有数据访问入口的 siteId 来源只能是 `resolveSite` 或 `requestSiteId`」**。

## H3 · `?? "default"` 绕过守卫

```ts
// src/extensions/theme/runtime-declarative.ts:444
runQuery: (params, sc) => runThemeQuery(env, params, sc, o.siteId ?? "default"),
```

`o.siteId` 类型是必填，所以 `??` 是**死代码**——但它是**活地雷**：
将来谁把 `siteId` 改成可选，这行不会报错，而是**静默切到默认站**。

同时暴露守卫缺口：

```js
// tests/architecture.test.mjs:244
/\b(siteId|locale)\s*(?::\s*[\w<>[\]| ]+)?\s*=\s*("default"|'default'|[A-Z][A-Z0-9_]{2,})\s*(?=[,)])/g;
```

只匹配 `= "default"` 形式 → **`?? "default"`、`|| "default"`、三元兜底全部漏网**。
`runtime-declarative.ts:225` 的 `String(scope.locale ?? "en")` 同理。

**建议**：守卫**扩到兜底运算符**（`\?\?|\\|\\|`）与三元分支；
并**注入一次违规反向验证**（这是本仓库的既定纪律）。零容忍应该覆盖
「用表达式达到默认值效果」的所有写法，否则它只是把问题从 `=` 挤到了 `??`。

## H4 · 内容语言的 `|| "en"` 字面量回退

```ts
api.ts:1027  const locale = String(url.searchParams.get("locale") || "en");   // search
api.ts:1207  String(b.locale || "en")                                        // revision 写入
api.ts:1209  url.searchParams.get("locale") || "en"                          // autosave 读
api.ts:1210  String(b.locale || "en")                                        // autosave 写
```

`savePost`（`api.ts:201`）**已经被修成**「回退到站点默认语言」，这四处却还是硬编码 `"en"`。
在默认语言为 `zh-CN` 的站点上：搜索查的是 `t.locale='en'`（空结果或错语言），
版本/自动保存**写进 en 行**——内容语言事实被悄悄改写。

**建议**：全部改为 `await siteDefaultLocale(env, siteId)`；并把「回退顺序恒为 当前语言 →
站点默认语言 → 空，不抛错」抽成**一个函数**（`resolveContentLocale(env, siteId, hint)`），
消除四处重复表达（规则 30：同一规则只表达一次）。

## 中危（不致命，但会拖垮「扩展强 / 不耦合」）

### M1 · `setSiteDefaultLocale` 的 500 路径

```ts
// api.ts:715  —— 未包 try/catch
if (b.is_default === true) await setSiteDefaultLocale(env, siteId, code);
// locale-registry.ts:264  —— 直接抛
if (!isLocaleCode(code)) throw new Error(`invalid locale code: ${code}`);
```

路由正则 `^i18n/locales/([A-Za-z0-9-]{2,10})$` 比 `isLocaleCode` **宽**：
`PATCH /api/v1/i18n/locales/12` 能过路由，却在 `setSiteDefaultLocale` **抛未捕获异常 → 500**。
紧邻的 `disableSiteLocale`（720）**包了** try/catch 返回 400。**同一路由两种错误处理**，
是「能放错」的典型：用户拿到 500 而不是「无效语言代码」。
（也违反不变量 6 的精神：语言解析/切换不该炸。）

### M2 · `_i18n` 表名的第二处表达式

```ts
// tables.ts:323
const i18nName = `${def.table_name}_i18n`;
```

权威定义是 `themeI18nTableName()`（`tables.ts:113`）。此处**重算**同一规则——
今天等价，改命名规则时会脱节（规则 30：同一规则只表达一次）。

### M3 · 主题 Worker 的表解析路径与其它路径不同

`runtime-worker.ts:410,442` 用 `resolveThemeTable(env, siteId, themeName, …)`，
**不**走 `resolveTableForSite`。后果：主题切换后，Worker 主题**够不到**已有表，
而后台/前台够得到。这不是命名绕过，是**两条解析路径**——「通用」的反面。

## 审查有错：两个结论在执行中被推翻

**1. H1 的第一版修法是错的（会崩）。** 我最初给侧表加了 `AND site_id = ?`——
但**读了真实 D1 才确认 `{table}_i18n` 根本没有 `site_id` 列**（键是 `row_id`+`locale`）。
照第一版发上去，**每次删除都会运行时抛错**。
正确做法是**先查主表验归属**（那是唯一能表达站点边界的地方）。
→ 教训：**"补个 WHERE"看起来总是对的；schema 要先读，不要按对称性推断。**

**2. M3 的判定被我改判：不是缺陷，是有意隔离。** 原审查说「主题 Worker 的表解析
与后台/前台不一致」。深入后发现差异是**故意的**——沙箱只能碰自己声明的表
（安全性），而 `resolveTableForSite` 会回退到站点上任意表。
统一它们会**削弱隔离**。因此未改该处，改为在 H2 里补上**主题激活绑定校验**，
从源头堵住伪造。

**3. 我自己新写的守卫踩了两次同样的坑**（已记入 `AGENTS.md`「第七种假绿」）：
   - 正则的尾 `\b` 在 `"default"` 的尾引号后**恒不成立** → 对真实写法全部漏配。
     修法：**逐写法实测**，不靠推断。
   - 豁免元守卫只统计「带标记**且有违规**」的文件 → 第二个文件无违规即可白拿豁免。
     修法：统计**标记本身**。
   → **一个只在"没违规时"才通过的检查，看不见自己的范围失控。**

# 第二轮：「所有数据必须有多语言能力」的强制（§10 规则 41）

> 用户要求：「**要超级严格。要强制该系统的所有数据都要有多语言的特性和能力**」。
> 第一轮的修复是**堵漏**（把已知的兜底/字面量清掉）；这一轮是**换机制**——
> 让「有多语言能力」从**约定**变成**安装边界上的硬校验 + 架构测试 + 脚手架默认值**。

## 原来漏在哪

多语言能力此前是**可选**的：`tables[].translatable` 写了就生效，不写就静默退化为单语言。
漏不掉的原因不是测试没跑，而是**测试问错了问题**——它检查「已经声明的字段是否被正确分类」，
却从不检查「字段有没有被声明」。于是一个新主题只写 `fields`、不写 `translatable`，
**安装成功、渲染正确、单语言下毫无异常**，直到启用第二种语言时才暴露——
那时修复成本已是「迁移 + 重译」。

这与 AGENTS.md 记录的「声明先于运行时」缺陷族**同型**：字段被校验、运行时没人读 → 200 + 内容错。

## 机制：一处定义，三处强制

分类是**词汇表**，不是判断逻辑。定义收在 `contract/manifest.ts` 一处，三个消费者共用：

```ts
export const PROSE_FIELD_TYPES = ["text", "longtext"] as const;              // 人读的散文
export const LANGUAGE_NEUTRAL_FIELD_TYPES = ["number", "boolean", "date", "datetime"] as const;
export function isProseFieldType(type: string): boolean;                     // 唯一谓词
```

| 层 | 位置 | 作用 | 为什么必须在这一层 |
|---|---|---|---|
| 安装边界 | `contract/validation.ts` | 第三方 zip 装不进来 | 架构测试**永远看不到**还没落盘的扩展 |
| 架构测试 | `tests/architecture.test.mjs` | 已发布的主题当场变红 | 报错能指名 `file:table:field`，且不需要 Worker |
| 脚手架 | `scripts/make-table.mjs` | 新主题**天生合规** | 生成器自己不守规则，规则就从第一天漏 |

**双向强制**（两个方向都校验，不是一个）：

```ts
// A 方向：散文必须声明
if (isProseFieldType(ft) && !declaredTranslatable.has(key)) fail(...);
// B 方向：语言中立不得声明
if (!isProseFieldType(ft) && declaredTranslatable.has(key)) fail(...);
```

B 方向常被当成多余。它不是——把 `price` 标成可翻译，等于**每种语言一个价格**，
是数据模型错误，只是不会崩。**「不报错」和「正确」是两件事。**

## 架构测试里的四道结构守卫（重点：防的是「将来」）

规则 41 的守卫如果只跑已发布的主题，那**新增第七种字段类型**时会全绿通过——
因为没有主题用它，集合是空的。**对空集合的检查是空转**（AGENTS.md 记载的第三种假绿）。
所以分类表本身也要被守：

| 守卫 | 防的是什么 |
|---|---|
| 两个列表**不重叠** | 同一类型同时是散文与中立 → `isProseFieldType` 的答案取决于查表顺序 |
| 每个允许类型**都被分类** | 新增字段类型若两表都不进，**静默逃出规则**，且所有主题都"合规" |
| 没有**幽灵类型** | 分类里写了 `ALLOWED_TABLE_FIELD_TYPES` 里不存在的类型 → 打错字无人发现 |
| **非空断言** | `langTablesChecked > 0`：改名/移动目录让 walk 扫不到清单时，**失败而不是庆祝** |

第三条**非空断言**是本轮最重要的守卫。没有它，把 `themes/` 改名会让
「所有主题都合规」恒真——又一个「恒真等于没断言」。

## 反向验证（`tests/_i18n-field-inject.mjs`，6 个场景）

工具，不进 `npm test`（与 `_eshop-inject.mjs` 同性质）。每个场景：
**注入前断言干净 → 注入并断言内容哈希变了（等长替换也看得见）→ 跑套件 →
断言"哪一条"红了（按名字，不是"红了几条"）→ 还原并再断言干净。**

| 场景 | 注入 | 红了 |
|---|---|---|
| 校验器 A 方向 | `if (false && isProse...)` | `prose` 缺声明（65/1） |
| 校验器 B 方向 | `if (false && !isProse...)` | 语言中立被误声明（65/1） |
| 词汇表：散文类型被删 | `["text"]`（丢 `longtext`） | 「每个类型都被分类」（20/2） |
| 词汇表：类型进两个表 | 中立表加 `longtext` | 「两表不重叠」（21/1） |
| 已发布主题 | 删一个 `translatable` 项 | 「translatable 恰为散文」（21/1） |
| 脚手架默认值 | `defaultTranslatable = []` | 「生成的散文可翻译」（66/5） |

6/6 通过。**每一条都证明自己会红**，而不是"看起来会红"。

## 顺带修的一处夹具（规则 41 抓出来的真问题）

`tests/i18n.test.mjs` 的夹具把 `sku` 声明为 `type: "text"`，却在注释里说它**跨语言共享**。
旧规则下合法（不写 `translatable` 即不翻译），新规则下**自相矛盾**：
`text` 是散文，必须可翻译；而 SKU 是标识符，必须跨语言一致。

修法是**改类型而不是加豁免**：`sku` 改成 `number`（语言中立类型）。
**这是规则在正确地工作**——它逼出了一个此前被掩盖的建模错误：
用 `text` 存标识符，等于宣称"这段文字值得翻译"。夹具的注释也一并改写了，
说明为什么是 `number` 而不是 `text`。

## 覆盖范围：清点之后还剩什么（`tests/_i18n-data-inventory.mjs`）

规则 41 覆盖 `tables[].fields[]`。清点全部已发布扩展后，**另有 12 处声明承载数据**：

| 类 | 数量 | 现状 | 判断 |
|---|---|---|---|
| `settings[]` | 10 | `theme_settings` 键为 `(theme_name, key)`，**无语言维度** | **仅后台可读**（前台无任何读取路径）→ 是**配置**不是内容 |
| `fields[]`（文章自定义） | 2 | 存 `post_meta`，键为 `(post_id, meta_key)` | 随 `posts.lang_group` 走 — 见下 |
| `taxonomies[]` | 1 | 声明了但**无 UI 接线** | 潜在（未被使用，故无语言维度可言） |
| `postTypes[]` | 1 | 内容语言由 `posts.lang_group` + `post_translations` 提供 | 已覆盖（L1） |

**结论（诚实版）**：`settings[]` **不是**漏洞——它只被后台读，前台没有任何读取路径
（`grep` 过 `src/rendering/`、`runtime-*.ts`、`public/admin/`）。给它加语言维度会变成
「声明了但运行时没人读」的字段——**正是本轮要消灭的缺陷族**。
已把该判断写进本文档，而不是加一个空字段。

**真正待定的一项**：文章自定义字段（`post_meta`）的语言归属。当前 `post_meta` 挂在
`post_id` 上，而每种语言的版本是**不同的 post 行**（L1 的 `post_translations`）——
所以「中文版的 price」在结构上已可独立存在，但**平台没有为它提供复制/回退路径**
（`post_translations` 只复制标题/正文）。是否补这条路径取决于产品是否要「自定义字段也可译」。
**已记录，未实现**——不做没被要求的字段。
